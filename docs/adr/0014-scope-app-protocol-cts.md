# ADR-0014 项目范围收敛为“App + 协议 + CTS + mock/最小参考 Agent”

- 状态：Accepted
- 日期：2026-11-19

## 背景

原设计是全栈项目（Android App + 完整 C++ Agent + 多形态适配 + rl_sar 补丁 + 深度/点云/地图），
约 20–24 周、3 人。实际目标是“一套手机操作端 + 标准协议口，机器人端按需实现 + 局域网自动发现”。
全栈实现会让项目维护面过大、进度慢，也让生态难以接入；纯 App 又会导致协议不可验证、碎片化。

## 决定

1. **项目定位**：标准协议 + Android 操作端 + 一致性测试（CTS）+ mock/最小参考 Agent。
2. **机器人端**：生产 Agent 由厂商/社区按 [18-protocol-implementation-guide.md](18-protocol-implementation-guide.md)
   实现；项目只提供“最小参考 Agent”（单形态、单相机、基础档）作为活文档，不承诺多形态/RL 集成。
3. **v1 仅 Android**，只交付“基础档”：发现/配对/会话/控制/遥测/视频/URDF 模型状态/安全语义；
   深度、点云/地图、关节/笛卡尔命令等作为 v1.1 增强档，按能力协商启用。
4. **自动发现**为协议一等公民：mDNS + UDP 广播 + QR/手动 IP 三通道；服务端实现成本约 20 行。
5. **安全边界**：App 不是安全边界；协议强制机器人端看门狗/急停/限位/仲裁，CTS 安全组作为接实机门槛。
6. 跨平台（iOS/桌面/Web）后置到 v1.x/v2，v1 不投入；共享层保持 KMP-ready 边界。
7. 路线图调整为 v1 约 10–14 周（2 人），v1.1 增强档约 3–4 周，v1.x/v2 跨平台另行规划。

## 理由

- 聚焦可验证的核心：协议 + 客户端 + CTS 能独立交付并被第三方采用；
- mock + 最小参考 Agent 提供“可跑通的活文档”，降低接入门槛、避免协议碎片化；
- 深度/点云/地图服务端实现成本高，先作为增强档，避免阻塞 v1；
- 自动发现是体验关键，且服务端成本极低，必须内置而非后补；
- 安全必须由机器人端实现，项目通过 CTS 强制而不是口头约定。

## 后果

- 项目不再提供“开箱即用的完整机器人 Agent”；用户需要按指南实现或等待社区实现；
- 深度/点云/URDF 的完整能力延后到 v1.1；v1 只保证基础档体验；
- 需要维护 CTS 与 mock，这会带来持续测试成本，但显著降低生态碎片化；
- 文档/验收标准需全面调整（00/01/07/10/16/17 等，本 ADR 落地时同步）。

## 备选

- 纯 App + 协议文档（不可验证，碎片化风险高，不采用）。
- 保持全栈（范围大、周期长，不采用）。
- 只做协议 + 参考 Agent、不做 App（与本项目目标不符）。
